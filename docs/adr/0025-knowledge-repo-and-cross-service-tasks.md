# ADR-0025: Мета-репа знаний и задача по нескольким сервисам

- Статус: предложено
- Дата: 2026-10-15
- Основание: [ADR-0017](0017-models-and-mcp-configuration.md) (конфигурация: машина и проект),
  [ADR-0020](0020-skills-and-standards.md) (знание, стандарты, навыки), [ADR-0021](0021-stack-agnostic-core.md)
  (скан и граф), [ADR-0023](0023-editor-and-web-ui.md) и [ADR-0024](0024-knowledge-in-web-ui.md) (`jarvis ui`),
  [ADR-0012](0012-evals-and-record-replay.md) (evals); пилот на бэкенде из многих микросервисов
- Мокап: страницы мастер-прогона и сабтасков (артефакт «Jarvis: задача по сервисам»)

## Контекст

Бэкенд — десятки микросервисов, каждый в своей репе. Сейчас Jarvis живёт в одной репе: там `.jarvis/project.yaml`,
знание `.jarvis/knowledge`, прогон работает в копии этой репы. Для бэкенда этого мало:
- знание должно быть сквозным: границы сервисов, кто отдаёт эндпоинт или топик и кто его потребляет, общий
  глоссарий;
- в репах сервисов не должно быть ничего от Jarvis: ни `.jarvis`, ни сгенерированных документов;
- задача часто задевает несколько сервисов: новое поле в событии меняет того, кто его шлёт, и тех, кто читает.

Команда платформы ведёт отдельную репу знаний. Изменения в неё идут через PR, конфликты решают люди. Репы у
разработчиков лежат рядом, в одной папке, но не у всех одинаково.

## Решение

### 1. Мета-репа — единственное место Jarvis

```
repos/
  jarvis-knowledge/            # мета-репа: владеет команда, изменения через PR
    .jarvis/
      project.yaml             # общее для всех сервисов + карта сервисов (§2)
      workflows/
    knowledge/
      landscape.md             # границы: домены, сервисы, владельцы — пишут люди
      glossary.md
      services/
        orders-api/            # знание сервиса: architecture, conventions, contracts, module-*.md
          contracts.json       # машинная часть contracts.md (§4)
        delivery-slots-api/
    evals/
  orders-api/                  # репы сервисов — без .jarvis
  delivery-slots-api/
  notify-api/
```

Всё, что Jarvis сейчас пишет в `.jarvis` репы (`onboard`, принятые модули, термины глоссария), пишется в мета-репу,
в `knowledge/services/<сервис>/`. Сам Jarvis в мета-репе не коммитит: страница и `jarvis status` показывают, что в
её рабочей копии изменено, и дают команду для ветки и PR. Сгенерированное (`contracts.*`, скан) пишется
детерминированно и отсортированно, по файлу на сервис, чтобы PR от разных людей реже конфликтовали.

Режим одной репы со своей `.jarvis` остаётся: мета-режим включается, когда в репе `.jarvis` нет.

### 2. Карта сервисов и конфигурация

```yaml
# jarvis-knowledge/.jarvis/project.yaml
version: 1
# ключи верхнего уровня — общее для всех сервисов (как project.yaml сейчас)
stack: [java, spring, mongo, kafka, gradle]
tools: { local: { test: ./gradlew test } }
workspace: { mode: worktree, checkout: clone, setup: ./gradlew classes testClasses -q }
repos: ..                       # где лежат репы; по умолчанию — папка над мета-репой
services:
  orders-api: {}                # репа ../orders-api (по имени папки)
  delivery-slots-api:
    repo: slots-service         # папка называется иначе
    tools: { local: { test: "TZ=Europe/Moscow ./gradlew test" } }
  notify-api:
    stack: [kotlin, spring, kafka, gradle]
```

- Сервис ищется по имени папки в `repos`; `services.<имя>.repo` задаёт другую папку (относительно `repos`) или
  путь.
- Раскладка у разработчика своя — она в личном конфиге: `~/.jarvis/config.yaml` → `repos: { delivery-slots-api:
  ~/work/slots }`. Порядок: личная карта, затем карта мета-репы, затем имя папки.
- `services.<имя>` принимает те же ключи, что `project.yaml` (`stack`, `tools`, `workspace`, `knowledge`,
  `security`, …). Слияние: пользователь → общее мета-репы → сервис.

### 3. Как Jarvis находит мета-репу и сервис

Запуск в репе сервиса без `.jarvis`:
1. мета-репа: `JARVIS_KNOWLEDGE`, иначе `knowledge.home` личного конфига, иначе соседняя папка, где есть
   `.jarvis/project.yaml` с `services:`;
2. сервис: тот, чья репа по карте (§2) — эта репа (`git rev-parse --show-toplevel`);
3. не нашлось — ошибка с подсказкой: `services.<имя папки>` в мета-репе или `repos` в личном конфиге.
   `jarvis doctor` проверяет карту целиком: каждая ли репа на месте, нет ли двух сервисов на одной папке.

Запуск в самой мета-репе — задача по сервисам (§6) или работа со знанием.

### 4. Знание сервиса и соседей

Прогону в сервисе S достаётся:
- знание S: `knowledge/services/S/**`;
- общее: `landscape.md`, `glossary.md`;
- соседи: сервисы, которые потребляют то, что отдаёт S, и те, у кого S берёт. Это карточки, а не модули целиком:
  имя, владелец, общие эндпоинты и топики.

Соседи считаются без модели. `onboard` в S пишет `contracts.json`: эндпоинты, которые S отдаёт; топики, куда шлёт и
откуда читает; HTTP-клиенты и их адреса; ключи конфига. Это то же, что сейчас собирает `codeContractsOf`. Каталог
по всем сервисам строится в памяти из всех `contracts.json` и не коммитится, так что конфликтовать нечему. Модули
чужих сервисов агент получает поиском, по запросу.

Шаг impact по каталогу видит, что задача меняет контракт (эндпоинт, топик, DTO), и пишет потребителей: «поле
`slotId` в `orders.created` читают notify-api, delivery-slots-api».

### 5. Входы прогона и evals

Прогон записывает коммит мета-репы и её незакоммиченные файлы знания так же, как сейчас `.jarvis` своей репы:
`git hash-object -w` в мета-репе, id — в `run.created`. Evals живут в мета-репе: `evals/<набор>/<кейс>/`, fixture —
`{ service, commit, knowledge: { commit, overlay } }`.

### 6. Задача по нескольким сервисам: мастер-прогон и сабтаски

Мастер-прогон ведёт задачу целиком, но в коде сервисов не работает. Работа идёт в сабтасках, по одной на сервис;
каждый сабтаск — обычный прогон sdd в своей репе.

Workflow `cross`:

| шаг | что | кто |
|---|---|---|
| research | по landscape, каталогу и графам сервисов (чтение) | модель |
| spec | одна спека задачи, гейт | модель, человек |
| split | сервисы, которые задеты (по каталогу), и предложение разбиения: сабтаски и контракт | детерминированно + модель |
| гейт разбиения | убрать или добавить сервис, поправить текст сабтаска, порядок поставки, контракт | человек |
| spawn | сабтаски-прогоны; каждому — спека, своя часть, контракт | детерминированно |
| wait | мастер ждёт сабтаски (`WAITING_CHILDREN`) | — |
| contract-check | каждая сторона контракта в своей копии: отдающий отдаёт, потребители вызывают с теми же методом, путём, топиком и полями | детерминированно |
| гейт поставки | Apply или PR по сервисам в порядке поставки | человек |

- Артефакты split: `split.json` — сабтаски `{ key, service, task, deliverAfter[] }`; `contract.json` — изменения
  `{ kind: endpoint | topic | dto, id, change, producer, consumers[] }`.
- Сабтаски стартуют параллельно (не больше `cross.maxParallel`, по умолчанию 2: квота моделей общая): контракт
  зафиксирован на гейте, и потребитель пишет код и тесты по нему, не дожидаясь поставщика. `deliverAfter` задаёт
  только порядок поставки: сначала отдающий сервис, обратно совместимо, потом потребители.
- Сабтаск — полноценный прогон: свои копия, ветка, гейты, Apply, пауза, отмена, «Run again». В нём видны мастер и
  его часть контракта.
- Сабтаск упал или отменён — мастер показывает это и даёт выбор: перезапустить сабтаск, убрать сервис из
  разбиения (вернуться к гейту), отменить задачу целиком.
- Контракт менять может только мастер. Если сабтаск понял, что контракт надо менять, он останавливается с запросом
  на изменение. Мастер показывает запрос на гейте, человек решает, и новый контракт уходит остальным сабтаскам
  заметкой (`addNote`).
- Бюджет мастера — сумма бюджетов сабтасков, его собственные шаги считаются отдельно.

Модель данных: у прогона `parent?: { runId, key }`; у мастера `waitingFor: { kind: "children" }`; событие
`run.spawned`.

### 7. Страницы

- **Runs:** мастер — одна строка с прогрессом «2 из 3», сабтаски раскрываются под ней.
- **Мастер-прогон:** шаги `cross`; план — сервисы и стрелки контракта; доска сабтасков: состояние, шаг, что ждёт
  человека, ветка; контракт со статусом проверки по каждой стороне; поставка.
- **Гейт разбиения:** спека слева, разбиение справа, с правкой.
- **Сабтаск:** крошки «ABC-42 › orders-api», его часть контракта, соседи по задаче.
- **New task:** в выборе репы — «All services · jarvis-knowledge».

### 8. Безопасность

Прогон сабтаска видит свою репу и знание мета-репы, остальные сервисы — только через карточки и каталог.
`security.deniedPaths` задаётся по сервисам. В мета-репу попадает только то, что прошло редактирование секретов
([ADR-0010](0010-secret-redaction.md)), как сейчас `.jarvis/knowledge`.

## Этапы

1. Мета-репа: поиск, карта, конфиг по сервисам, знание по сервисам, запись `onboard` и модулей в мета-репу,
   входы прогона. Задачи по-прежнему в одном сервисе.
2. `contracts.json`, каталог, соседи в контексте, потребители в impact.
3. Мастер-прогон `cross`, сабтаски, проверка контракта, страницы (§7).
4. Evals в мета-репе.

## Последствия

- В репах сервисов ничего от Jarvis; команды подключаются строкой в карте.
- Знание ревьюится как код, через PR в одну репу.
- Задача по сервисам — несколько небольших прогонов в одной репе каждый: контекст узкий, и с этим справляются
  слабые модели.
- Новое: мета-режим загрузки конфигурации, сабтаски в модели данных, проверка контракта по коду двух репозиториев.
- Без доступа к мета-репе Jarvis в сервисе работать не может. В одиночном режиме остаётся `.jarvis` в репе.

## Альтернативы

- **`.jarvis` в каждой репе сервиса.** Знание расползается по репам и ревьюится в каждой отдельно, сквозного
  каталога нет; команда не хочет файлов Jarvis в сервисах.
- **Один прогон на несколько реп.** Копии и тесты всех сервисов в одном контексте: на слабых моделях не работает,
  Apply и откат размазаны по репам.
- **Каталог контрактов как закоммиченный файл.** Каждый `onboard` правил бы один общий файл, и PR конфликтовали
  бы. Каталог строится из файлов по сервисам.
- **Монорепо или git submodules.** Меняют то, как команды работают с кодом, ради инструмента.
